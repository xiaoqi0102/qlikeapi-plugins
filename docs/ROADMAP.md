## 计划中（欢迎 PR）

- [ ] **按成功率智能选路**：给渠道维护健康分（滚动成功率 / 平均延迟），
      自动成链时按健康分排序，而不是只看优先级
- [ ] **会话亲和（sticky）**：同一调用方短时间内优先命中上次成功的渠道，
      减少上游侧的「同图不同样」现象
- [ ] **价格页批量导入/导出（CSV）**，以及从上游账单文件对账
- [ ] **请求日志的留存策略**：按天数/条数自动清理（现在要手动）
- [ ] **渠道实例分组与标签**，渠道多了之后按组筛选/批量操作
- [ ] **Webhook 通知**：渠道熔断、余额低于预警线时推送到飞书/企业微信/Telegram
- [ ] **可选 Postgres 后端**（保留 SQLite 为默认），给需要多进程/高并发的场景
- [ ] **图片结果的可选转存**（显式开关，默认关闭）：上游给的是 7 天过期的签名 URL，
      需要长期保存的用户可以开这个开关转到自己的对象存储

## 明确不做（附理由）

| 不做 | 理由 |
|---|---|
| 用户体系 / 注册 / 充值 / 兑换码 / 邀请返利 | 这是自用网关，不是 SaaS；一上用户体系就要处理一整套越权与计费争议 |
| 拼车共享 / 多账号池 | 涉及上游 ToS 风险；本项目已有「多 key 轮换 + 冷却 + 熔断」，够用 |
| 语义缓存 / token 级计费 | 图片按张计费；缓存图片＝转存（与「不落盘」冲突），token 计费对图片无意义 |
| 用 New API 的插件机制实现 | 实测受限：路由与静态路由重叠会被整份拒绝、宿主协议表没有图片项、全局钩子被拒、请求体 1 MiB 上限 |
| 引入 Redis / Postgres 作为默认依赖 | 单机自用，SQLite 足够；多一个组件多一份运维负担（可选支持见上） |
| 复刻 gpt-load 的全套分组/计费模型 | 只需要它的「密钥池细节」（多 key 轮换 + 冷却），不需要它的分组与计费设计 |
| 内置任何上游的「签到 / 白嫖」脚本 | 与上游 ToS 冲突，且与本项目的职责（协议转换）无关 |
| 默认开启图片转存 | 「不落盘」是刻意设计：省磁盘、无隐私风险、无带宽成本 |

## 怎么提需求

开 issue 说清三件事：**你要解决什么问题**（不是「加个功能 X」）、
**现在的做法为什么不行**、**期望的接口/交互长什么样**。
路线图里的条目也欢迎直接 PR —— 先开 issue 对齐设计，再动手，避免白写。
