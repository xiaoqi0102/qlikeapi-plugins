# 尺寸换算规则（客户端像素 → 上游实际尺寸）

> 本文件回答一个问题：**客户端传 `size` 之后，本服务到底会向上游要什么尺寸、最后出多少像素。**
> 两套上游协议完全不同，所以规则也分两套。所有数字都有官方出处，不是我们编的。

## 一、GPT-Image-2 / 2.5 系（change2pro-image2、七牛同步面、fal gpt 面）——「自由尺寸」

上游允许任意 `WIDTHxHEIGHT`，但有 **4 条硬限制**（出处：Azure OpenAI《GPT image models》文档，
`GPT-Image-2 / 2.5-Flare / 2.5-Sunburst` 段落）：

| 限制 | 值 |
|---|---|
| 宽和高都必须能被 **16 整除** | `1920x1080` ❌（1080 ÷ 16 = 67.5） |
| 长短边比 | ≤ **3:1** |
| 任一边最长 | ≤ **3840 px** |
| 总像素 | **655,360 ~ 8,294,400** |
| 附加说明 | > `2560x1440` 属上游**实验档** |

`gpt-image-1` / `1.5` / `1-mini` **不适用**上面这套 —— 它们只认三种尺寸：
`1024x1024` / `1536x1024` / `1024x1536`（本服务在这三种里挑比例最接近的）。

### 我们的吸附策略：**最小改动，绝不放大**

旧版是「不合法就按比例跳到最近的标准档」，于是 `1920x1080` → `2048x1152`（像素 +13.8%）。
上游按 1K/2K/4K 分档计费时，这就是**多扣费**。现在改成：

1. 合法 → **原样透传**（`2048x1152`、`3840x2160`、`1024x1024` 都不动）；
2. 不合法 → **保留合法的那一边，只把不合法的那一边就近修成 16 的倍数**，平手时向下取
   （宁可略小，也不越档）：`1920x1080` → **`1920x1072`**；
3. 只有真的出界（比例 > 3:1、边长 > 3840、面积超上限/不足下限）才等比缩放，
   取整后若又顶出界会再微调一次，直到真合规。

实测样例：

| 客户端传 | 旧版结果 | 现在 |
|---|---|---|
| `1920x1080` | `2048x1152`（+13.8% 像素） | **`1920x1072`**（-0.7%，同档同价） |
| `1000x1000` | `1024x1024`（放大） | **`992x992`**（略小） |
| `2048x1152` | `2048x1152` | `2048x1152`（本来就合法） |
| `3840x2160` | `3840x2160` | `3840x2160`（面积正好顶上限，合法） |
| `4096x4096` | `1024x1024`（跳到 1:1 标准档） | **`2880x2880`**（等比缩到合法，仍 1:1） |
| `400x400` | 视情况 | **`816x816`**（面积补到下限 655,360 以上） |

被换算时：响应头 `X-QLike-Size: 1920x1080->1920x1072`，中文说明写进请求日志详情。

## 二、Gemini 3 图片模型（change2pro 香蕉面、七牛 fal gemini 面）——「档位 + 宽高比」

**Gemini 给不了任意像素**：只能指定【分辨率档位 + 固定宽高比】，模型按该比例的标准像素出图。
出处：Google `ai.google.dev` 图片生成文档（`#aspect_ratios_and_image_size`）。

档位：`0.5K`(512px 基准) / `1K`(1024px) / `2K`(2048px) / `4K`(4096px)。
本服务把客户端像素先换算成【比例】再换算成【档位】：

- 比例：按 `w/h` 取最接近的支持比例（见下表）；
- 档位：默认 `class` 策略 —— 按**尺寸档位分类**（相邻档位标称边的对数中点 724 / 1448 / 2896 分界），
  也就是客户端认知里的「≤1K / ≤2K / ≤4K」。所以 `1920x1080 → 2K`、`3840x2160 → 4K`、
  `1024x1024 → 1K`、`512x512 → 0.5K`。

### Gemini 3.1 Pro Image（`gemini-3-pro-image` / `-preview`）

只支持 `1K` / `2K` / `4K`，且**不支持** `1:4` / `4:1` / `1:8` / `8:1` 这四个极端比例
（客户端传 8:1 会被收敛到最接近的 `21:9`）。

### Gemini 3.1 Flash Lite Image

只支持 `1K`，其余档位请求会被收敛到 1K。

### 档位策略（渠道实例 `options.gemini_size_policy`，面板下拉可选）

| 策略 | 含义 | `1920x1080` 的结果 |
|---|---|---|
| `class`（默认） | 按尺寸档位分类，与客户端认知一致 | `16:9 · 2K · 2752x1536` |
| `floor` | 向下取档（**最省**，按档计费时最便宜） | `16:9 · 1K · 1376x768` |
| `nearest` | 取最接近档（按实际输出边长对数距离） | `16:9 · 1K · 1376x768` |
| `ceil` | 向上取档（**不降级**，绝不小于请求） | `16:9 · 2K · 2752x1536` |

> 注意：Gemini 的 2K 在 16:9 下输出 **2752x1536**（4.2MP），比客户端要的 1920x1080 大一倍多。
> 如果某个渠道按 1K/2K/4K 分档计费，且你不想为「被升档」付钱，就把该渠道的策略设成 `floor`。

## 三、怎么自己验证（零成本，不出图）

1. 面板「模型目录」页底部 **尺寸换算**：填模型名 + 尺寸 + 策略 → 直接看结果与说明；
2. 接口：`GET /api/size-plan?model=gemini-3.1-flash-image&size=1920x1080&policy=class`；
3. 干跑：`GET /v1/route-preview?model=xxx`（看路由链），真实请求的换算结果看请求日志详情
   与 `X-QLike-Size` 响应头。
